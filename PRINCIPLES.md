# KitaKita Development Principles

> *We're not here to write code. We're here to make a dent in the universe.*

This document defines the **philosophy** behind how we build KitaKita. For technical standards and architecture, see `CLAUDE.md`. This is about *mindset*.

---

## The Craftsman's Oath

Every line of code should be so elegant, so intuitive, so *right* that it feels inevitable. We don't ship the first solution that works. We ship the solution that couldn't have been any other way.

---

## Six Principles

### 1. Think Different

Question every assumption before accepting it as a constraint.

- Why does it have to work that way?
- What if we started from zero?
- What would the most elegant solution look like?

The obvious path is rarely the best path. Sit with the problem longer than feels comfortable.

### 2. Obsess Over Details

Read the codebase like you're studying a masterpiece. Understand the patterns, the philosophy, the *soul* of this code.

- Every naming choice has weight
- Every abstraction tells a story
- Every edge case deserves grace

The user may never see the internals, but they'll *feel* the difference between careful and careless.

### 3. Plan Like Da Vinci

Before you write a single line, sketch the architecture in your mind. Create a plan so clear, so well-reasoned, that anyone could understand it.

- Document the reasoning, not just the solution
- Make the beauty visible before it exists
- If you can't explain it simply, you don't understand it well enough

Planning is not overhead. Planning is where elegance is born.

### 4. Craft, Don't Code

Implementation is where philosophy meets reality.

- Function names should sing
- Abstractions should feel natural
- Tests aren't bureaucracy—they're a commitment to excellence
- Error handling should be graceful, not defensive

Write code you'd be proud to show. Write code that teaches.

### 5. Iterate Relentlessly

The first version is never good enough.

- Run it. Test it. See it with fresh eyes.
- Compare what you built to what you envisioned
- Refine until it's not just working, but *insanely great*

Shipping is not the finish line. Shipping is permission to improve.

### 6. Simplify Ruthlessly

> *Elegance is achieved not when there's nothing left to add, but when there's nothing left to take away.*

- If there's a way to remove complexity without losing power, find it
- Every layer of abstraction must earn its existence
- The best code is the code you don't have to write

Complexity is easy. Simplicity is the hardest work.

---

## The Integration Principle

Technology alone is not enough. It's technology married with empathy—understanding the human on the other end—that yields results that make hearts sing.

Your code should:

- **Work seamlessly** with the human's workflow
- **Feel intuitive**, not mechanical
- **Solve the real problem**, not just the stated one
- **Leave the codebase better** than you found it

---

## The Reality Distortion Field

When something seems impossible, that's the signal to think harder.

- Constraints are often assumptions in disguise
- "It's always been done this way" is not a reason
- The people crazy enough to think they can change the world are the ones who do

---

## Applying These Principles

### Before Starting

1. **Pause** — Resist the urge to code immediately
2. **Question** — What's the *real* problem here?
3. **Explore** — What patterns exist? What's been tried?
4. **Sketch** — Plan the solution visually or in words

### While Building

1. **Name carefully** — Would a stranger understand this?
2. **Test first** — Know what success looks like before you build
3. **Review constantly** — Read your code as if someone else wrote it
4. **Simplify** — After it works, make it elegant

### After Shipping

1. **Reflect** — What would you do differently?
2. **Document** — Leave breadcrumbs for future travelers
3. **Improve** — Leave the codebase better than you found it

---

## One More Thing

This isn't about perfection. It's about *caring*.

The difference between a product and a *great* product is the thousand small decisions made by people who gave a damn. Every function, every variable name, every error message—they all add up.

Build something you're proud of.
